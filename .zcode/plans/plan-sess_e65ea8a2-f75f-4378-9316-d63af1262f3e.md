# Phase 2 — Accounting Correctness

Goal: make the ledger actually reflect shop finances, with a GAAP-standard finalize/void model. Driven by flipping the four Phase-1 characterization tests + adding new positive tests.

Decisions baked in (from your answers):
- **Payments**: deposits + payments. Pre-finalize money = liability (Customer Deposits); post-finalize money = debit Cash, credit A/R.
- **Edits after finalize**: lock financials; allow notes/contact edits; corrections require void-and-replace.
- **Void**: reversing transaction + `'Voided'` status. Audit trail preserved.
- **Idempotency**: status-check guard, backed by a new `posted_tx_id` column that also serves as the lock signal and the reversal anchor.
- **Status strings**: unify to pipeline strings (`'Closed'`, not `'Finalized'`); use `posted_tx_id` to track "is posted" separately.

## 2.2 Core: rewrite `finalizeInvoice` (`core/db_manager.cpp`)

New behavior, in order:
1. **Idempotency guard**: `SELECT posted_tx_id FROM invoices WHERE id = ?`. If non-NULL → return `false` (caller shows "already finalized"). Fixes **C6**.
2. **Integer math**: replace every `(int64_t)(double * rate)` with `(parts_total_cents * tax_bps + 5000) / 10000` style integer rounding (tax_bps stored as basis points, e.g. 825 = 8.25%). Same for shop supplies. Fixes **H1**.
3. **Classification by `item_type`**: read `item_type` (not `specification`) from the items query. Bucket Part/Labor/Fee/Sublet/Discount correctly. Fixes **H3** for the core path.
4. **Compute totals** (all int64 cents): parts_retail, labor, fees, discounts, taxable_parts, tax_liability (rounded), shop_supplies (rounded, clamped), invoice_total.
5. **Begin transaction**. (Check `BEGIN` return value — fixes **H7**.)
6. **Post splits** with the corrected account mapping:
   - Debit **Accounts Receivable** `+invoice_total` (was: Checking — fixes **C2**)
   - Credit Parts Income `−parts_retail`
   - Credit Labor Income `−(labor + shop_supplies)` *(supplies still folded into Labor Income; dedicated account is Phase 6)*
   - Credit Sales Tax Liability `−tax_liability`
   - Debit COGS `+parts_cost_cents`; Credit Parts Inventory `−parts_cost_cents`
   - **If `prepayment_cents > 0`** (fixes **C3**): Debit Customer Deposits `−prepayment_cents` (reduces the liability — note sign), Credit Accounts Receivable `−prepayment_cents`. Net effect: the A/R balance owed drops by the prepayment, and the deposit liability is consumed.
7. Capture `tx_id = last_insert_rowid()`.
8. **Write back**: `UPDATE invoices SET status='Closed', posted_tx_id=? WHERE id=?`. (Status unified to pipeline string — your "Unify to pipeline strings" decision.)
9. **Commit**.

The splits still balance arithmetically — the existing `finalize_invoice_posts_balanced_splits` test stays passing.

## 2.3 Core: new `voidInvoice` method (`core/db_manager.cpp` + `.h`)

```cpp
bool voidInvoice(int invoice_id);  // returns false if not posted / already voided
```
Behavior:
1. `SELECT posted_tx_id, status FROM invoices WHERE id=?`. If `posted_tx_id IS NULL` → return false (nothing to reverse). If `status == 'Voided'` → return false.
2. Load the original transaction's splits.
3. **Begin transaction.** Insert a new `transactions` row: date=today, description=`"VOID — Reversal of Invoice #N"`.
4. For each original split, post the **mirror**: `INSERT INTO splits (...) VALUES (?, ?, -original_amount)`. This zeroes out every affected account while leaving the original post visible in the audit trail.
5. `UPDATE invoices SET status='Voided', posted_tx_id=NULL WHERE id=?`. (Clears `posted_tx_id` so the invoice is no longer "posted"; the original transaction remains in the ledger for history.)
6. **Commit.**

This is the GAAP-standard pattern (GnuCash calls it a "reverse transaction").

## 2.4 Core: new `recordPayment` method (`core/db_manager.cpp` + `.h`)

```cpp
bool recordPayment(int invoice_id, int64_t amount_cents,
                   const std::string& method, const std::string& reference);
```
Behavior depends on whether the invoice is posted:

- **Posted invoice** (`posted_tx_id != NULL`): money received against a finalized invoice.
  - Debit Checking `+amount`, Credit Accounts Receivable `−amount`.
  - Posts a `transactions` row: `"Payment — Invoice #N ({method} {reference})"`.

- **Not posted**: a pre-finalize deposit.
  - Debit Checking `+amount`, Credit Customer Deposits `−amount`.
  - Also bumps `invoices.prepayment_cents += amount` (so the UI's "Prepayments" / "Balance Due" reflects it).

Both branches balance. Method/reference are stored in the transaction description (no new columns — keeps schema lean).
